这份文档是 ZOS Web UI 的设计语言和变更约束。新增或修改前端界面时，默认必须遵循本文；具体业务需求可以改变信息内容和流程，但不能无意中改变产品的视觉性格、布局层级或交互语义。

实现细节以 `sourceOfTruth` 中的代码为准。当文档和代码不一致时，先修正文档或明确记录设计变更，再继续扩展组件；不要在局部 CSS 中悄悄建立第三套规则。

## 1. 产品性格

ZOS 是运行在个人 Linux NAS 上的本地运维工作台，不是营销页，也不是装饰性 dashboard。界面必须优先服务于扫描、比较、定位和重复操作。

- **紧凑但可读**：信息密度高，保留清晰的分组、对齐和可点击边界。
- **安静、工具化**：减少装饰性卡片、渐变、插画和大面积留白；状态和操作比氛围更重要。
- **暖色、克制、有辨识度**：暖白和炭黑表面承载高密度信息，珊瑚色只用于品牌、主操作、选中和焦点，不扩散成单色主题。
- **浅色首访，完整支持深色与跟随系统**：没有已保存偏好时使用浅色；用户仍可明确选择浅色、深色或跟随系统。三种偏好共享结构和交互反馈。
- **明确的风险层级**：主操作、普通操作、危险操作、等待审批、执行中、成功、失败必须可以通过颜色、图标和文字同时辨认。
- **本地系统感**：状态文案短、直接、可操作；避免营销语气和“体验式”描述。

不应出现：巨型 hero、宣传 banner、无意义的渐变背景、把普通状态包成装饰卡片、为了视觉效果而放大的标题、隐藏操作含义的图标。

## 2. 布局骨架

### 桌面

根布局是左右两个工作区：左侧 Agent，右侧 Workspace，中间保留可键盘操作的分栏拖拽区。

- `.app-shell` 使用全视口高度，左侧 Agent 最小宽度为 `560px`，右侧 Workspace 最小宽度为 `460px`。
- Agent 内部固定为 `68px` 图标栏和聊天主区；图标栏不展示长文本导航。
- Workspace 内部使用主内容区和面板导航栏，面板内容可以滚动，但页面骨架不应因内容增长而跳动。
- 面板、表格、预览和弹窗使用现有 `--surface`、`--channel-bg`、`--dialog-bg` 等语义背景，不直接创建新的颜色族。
- 操作栏与数据列必须留出可感知的间距。表格中的操作按钮组不能贴住 `SIZE`、时间或状态列；列宽不足时应进入已有响应式策略，而不是压缩按钮点击区域。

### Agent 栏

- 顶部只展示 ZOS 图标，不使用长 banner 代替导航。
- 会话以图标为主，当前会话使用持久高亮和左侧强调线。
- 状态指示器、通知入口和系统设置固定在栏底部；同一个功能不要在窄屏顶部重复出现。
- 通知按钮显示未读徽标，设置按钮和通知按钮保持相同的图标按钮尺寸、圆角和焦点状态。

### 窄屏

当前响应式边界具有明确职责，不要随意新增近似断点：

| 边界 | 规则 |
| --- | --- |
| `1040px` | 切换为单列；顶部只保留“聊天 / 工作区”主视图切换；Agent 底部的通知和设置仍是唯一入口。 |
| `860px` | 设置弹窗切为上下结构，设置导航变为横向滚动。 |
| `620px` | 管理区和文件区进一步收窄，标题、搜索和操作区改为可堆叠布局。 |
| `520px` | 预览模式下隐藏次要文件列，保持文件名和核心操作可用。 |
| `360px` | Composer 的主次按钮收窄为图标按钮，不能让输入区或发送操作溢出。 |

窄屏验收必须覆盖 `820/560/390/320px`。顶部主视图切换不是第二套导航，不能再放通知、设置等已存在于 Agent 底部的重复入口。

## 3. 品牌与标志

ZOS 的视觉方向借鉴 Anthropic / Claude 产品的温暖、编辑感和克制层级，但不得复制其商标、星芒图形或专有字体。品牌资产必须保持 ZOS 自己的名称和识别特征。

- 主标志是 `apps/web/public/zos-icon.svg` 中的原创交错单线 Z：上下回环与两条平行斜线构成折叠带状结构。标准色为珊瑚色 `#d97757`；深色界面通过周围主题令牌提供对比，不为标志建立蓝紫版本。
- 产品栏在空间受限时只显示标志；设置、文档和较宽品牌位使用“标志 + ZOS 文字”组合。文字标识由真实文本渲染，不另存栅格图片。
- 标志周围至少保留约四分之一图标宽度的净空，不能拉伸、加渐变、改成 Claude 星芒或与第三方品牌并置成联名标记。
- README、Web favicon、启动界面和文档站使用同一套 SVG 源形态；需要复制到不同构建目录时，路径可以不同，几何和颜色必须同步。

## 4. 视觉令牌

### 字体与层级

字体通过 Fontsource 随产品自托管，不依赖运行设备或外部 CDN。界面与文档站使用同一套家族：

- 界面正文：`Inter Variable` + `Noto Sans SC Variable`，回退到系统无衬线字体。
- 展示标题与 ZOS 文字标识：`Newsreader Variable` + `Noto Serif SC Variable`，仅用于标题、空状态主句和品牌文字。
- 代码、路径、命令和技术标识：`JetBrains Mono Variable`，回退到系统等宽字体。

同一区域最多组合正文和展示两种角色。中文必须使用对应的 SC 字体回退，禁止为了接近第三方品牌而引入未授权专有字体。

- 页面和工具正文：紧凑的 `12-14px`，以可读性为先。
- 面板标题：短、明确，使用现有标题层级，不使用 hero 级字号。
- 辅助标签和 eyebrow：小号、大写或短中文标签，用于分组和状态，不承担主要说明。
- 长文件名、路径、错误信息必须使用省略或换行策略，不能撑大表格和按钮。

### 颜色

所有颜色优先使用 `base.css`、`theme.css` 中的语义变量。当前语义角色如下：

| 角色 | 令牌方向 | 用途 |
| --- | --- | --- |
| 主强调 | `--accent`、`--accent-hover`、`--accent-contrast` | 品牌标志、主按钮、当前选中、关键链接和 Agent 当前项。 |
| 普通表面 | `--surface`、`--surface-hover`、`--surface-strong` | 次按钮、行 hover、工具区和控件表面。 |
| 中性文本 | `--text`、`--muted`、`--muted-2` | 主文本、辅助文本、禁用前的弱化信息。 |
| 成功 | `--green`、`--success-*` | 就绪、完成、健康。 |
| 警告 | `--yellow`、`--warning-*` | 等待、注意、能力缺失但可配置。 |
| 危险 | `--red`、`--danger-*` | 删除、失败、离线和不可逆风险。 |

基础主题为暖白、暖灰、炭黑和珊瑚，不使用旧版蓝紫作为品牌色。语法高亮、图表和文件类型可以使用多色语义，但不能让蓝紫重新成为大面积界面强调。

不要在组件中直接写新的蓝色、紫色、红色或灰色来“微调”现有主题。需要新语义时，先增加主题令牌并同时定义深色、浅色值；强调、成功和危险填充必须配套使用 `--accent-contrast`、`--success-contrast`、`--danger-contrast`，不要假定白字在两套主题中都可读。

### 尺寸与形状

- 交互控件通常使用 `6-8px` 圆角，避免大圆角胶囊化。
- 图标按钮需要稳定的宽高；桌面 Agent 按钮通常为 `40px`，普通工具按钮遵循所在工具栏的既有尺寸。
- 常用间距沿用 `4/6/8/10/12/14/18px` 的紧凑节奏，新增布局先复用邻近模块的间距。
- 卡片只用于确实需要被框定的交互单元、审批卡、弹窗和重复项；页面大区使用无框布局或完整面板，不要卡片套卡片。

### 文档站

Starlight 文档站通过 `docs/src/styles/custom.css` 映射同一字体、暖色表面和珊瑚强调。文档可使用更宽松的正文行高，但不能另建蓝色或紫色品牌主题；代码区继续使用等宽字体，导航与正文分隔必须在深浅主题中清晰可见。

## 5. 交互状态

所有可交互元素必须能区分默认、hover、active、focus、selected、disabled 和 busy 状态。统一状态实现位于 `interactions.css`，局部模块只补充业务语义，不得覆盖基本语义。

- **Hover**：提升文字对比度，并改变背景、边框或克制的阴影。
- **Active**：颜色进一步加深，阴影收紧，向下位移 `1px`；禁止放大按钮。
- **Focus-visible**：使用统一的 `2px` 高对比焦点环，键盘操作不能依赖 hover。
- **Selected / pressed**：使用持久的强调背景或边框，不能只复用临时 hover。
- **Disabled**：中性背景、边框和文字，不保留饱和主色，不响应 hover/active，指针为 `not-allowed`。
- **Busy**：保持控件尺寸稳定，设置 `aria-busy="true"`，显示 spinner 或忙碌图标，指针为 `progress`。
- **Reduced motion**：`prefers-reduced-motion: reduce` 下关闭位移和非必要状态动画。

交互过渡使用约 `120-160ms` 的现有控制令牌。触屏环境不能依赖粘滞 hover；桌面 hover 样式应放在 `@media (hover: hover) and (pointer: fine)` 中。

### 控件规则

- 使用 `lucide-react` 中已有图标；不要为常见操作手绘 SVG。
- 纯工具操作优先使用图标按钮，并提供 `aria-label` 和 `title`；明确命令可以使用图标加短文本。
- 可点击元素必须是真实 `button`、链接、选择器或具有完整键盘语义的角色元素，不要用普通 `div` 冒充按钮。
- 文字输入保留文本光标，拖拽分栏保留 `col-resize`，禁用控件不显示手型。
- 菜单、标签页、可点击行和自定义选择器必须同步 `aria-selected`、`aria-pressed` 或对应语义属性。
- Escape 应关闭当前弹窗、抽屉或菜单，并把焦点恢复到触发它的控件。

## 6. 核心界面约束

### Agent 与聊天

聊天区只承载用户主动发送的消息、Agent 回复和可操作审批卡。文件、Docker、VM、存储、共享等操作生命周期显示在持久通知中心，不伪装成用户消息。

- 用户消息、Agent 消息、系统状态和审批卡必须有明确的视觉边界。
- 会话标题和 transcript 只从真实用户消息生成。
- 通知中心从 Agent 栏底部打开，桌面使用约 `380px` 的侧边抽屉，移动端占满可用宽度。
- 通知项按更新时间倒序；未读项有克制标识；点击单条只读该条，不跳转、不意外关闭抽屉。

### Workspace 与文件

Workspace 是操作工作区，不是装饰性资源卡片。文件列表、预览、终端、下载、Docker、VM、网络、存储和共享面板应共享相同的标题、工具栏、状态和错误处理语言。

- 面板页头统一使用三段式结构：左侧图标，中间上下两行展示主标题和副标题，右侧使用 `PanelHeaderActions` 放置直接操作。
- 页头操作统一使用 `32px` 方形图标按钮和 `5px` 圆角，不显示按钮文字；每个按钮必须同时提供本地化的 `aria-label` 和 `title`。忙碌状态替换图标但不能改变按钮尺寸。
- 页头不展示 eyebrow、连接状态、运行状态、统计数据或其他辅助信息；不要为了保留这些信息新增独立状态徽标或工具栏，必要的业务状态由正文内容自然承载。
- 工作区容器窄于 `620px` 时，图标和标题保持第一行，操作区换到第二行并右对齐；不能缩小点击区域、挤压标题或产生横向滚动。
- 文件列表使用稳定的网格列：名称、操作、大小、修改时间；排序按钮是可访问的真实按钮。
- 文件搜索默认保持紧凑单行；高级筛选从 `SlidersHorizontal` 图标按钮打开，菜单承载类别、MIME、时间、大小、提取来源/状态和排序，不在主工具栏长期占据多行空间。Escape 关闭菜单并恢复焦点。
- 搜索结果正文只渲染纯文本和结构化高亮范围，不注入服务端 HTML；snippet 最多显示两行。分页使用稳定的“加载更多”操作追加结果，不改变当前筛选、排序或已有行的位置。
- 文件操作集中在操作列，按钮组右侧保留可感知间距，不能贴住 `SIZE` 或时间列。
- 行 hover、选中、禁用和键盘 focus 必须有区别；危险操作使用危险语义而不是单纯改变图标。
- 文件名、路径、端口、镜像名等长内容使用省略、title 或安全换行，不能造成布局抖动。
- 加载使用骨架或明确状态；不可用能力要说明原因并提供配置入口，不能只显示灰色不可点击按钮。

### 管理面板布局

Docker、虚拟机、网络、存储和共享面板使用同一套可编辑组件网格。页头和主操作保持固定，不进入网格；状态由概览或正文组件承载，概览、指标和顶层管理区作为独立组件参与排列，组件内部的表格行、共享目录和协议设置不单独拆分。

- 默认状态只展示业务内容；用户主动进入“编辑布局”后才显示拖拽抓手和右下角缩放手柄。
- 布局变化立即保存在当前浏览器。每个面板独立存储，并提供“重置布局”恢复默认排列；不提供隐藏或折叠组件。
- 鼠标拖拽只能从抓手开始，避免与表格选择、输入和滚动冲突。键盘聚焦抓手后，方向键移动组件，`Shift + 方向键` 调整尺寸。
- 管理面板容器宽度小于 `620px` 时固定为单列内容流，禁用拖拽和缩放；移动端仍按已保存布局的视觉顺序展示全部组件。
- 缩小组件不能挤压页面骨架；内容超出时在组件内部滚动。编辑提示使用现有强调色和边框，不给业务卡片再套装饰性卡片。

### 设置、弹窗与抽屉

- 弹窗必须有标题、关闭按钮、焦点管理和 Escape 关闭行为。
- 设置侧栏用于稳定导航，移动端切换为横向导航，不要在窄屏强行保留桌面双栏。
- Indexer 设置沿用紧凑字段网格；并发和限制使用数字输入，OCR 使用逐 root 复选框，重建是每个 root 的明确命令。服务、watcher、queue 和 rebuild 状态放在同页状态区，不与编辑字段混排。
- 破坏性操作需要明确的二次确认，确认按钮使用危险样式，取消操作保持低强调。
- Toast 只用于短暂反馈，固定在整个视口顶部居中并自动消失，不属于 Agent 或 Workspace 的内容流；需要跨设备、可追溯或伴随操作生命周期的内容进入持久通知中心。

## 7. 文案与本地化

- 所有用户可见文案进入 `apps/web/src/i18n/resources.ts`，组件不写只存在于单一语言的硬编码文案。
- 中英文都要保持短、直接、以动作为中心；同一操作在不同面板使用同一翻译键或同一术语。
- `Agent`、`Workspace`、`Docker`、`VM`、`NAS` 等产品和技术名词保持稳定，不要在不同页面随意改写。
- 错误文案说明发生了什么、用户能做什么；不要泄露凭据、内部路径或不必要的堆栈。

## 8. 无障碍基线

- 所有操作可用键盘完成，Tab 顺序与视觉顺序一致。
- 图标按钮必须有可读标签；装饰图标设置 `aria-hidden="true"`。
- 焦点环在深浅主题中都要可见，不能通过 `outline: none` 取消而不提供替代方案。
- 状态变化使用合适的 `role="status"`、`role="alert"` 或 `aria-live`，但不要让每次后台刷新都打断屏幕阅读器。
- 不能只靠颜色表达成功、警告、失败或选中；同时提供图标、文字或语义属性。
- 对话框打开时焦点进入对话框，关闭后恢复触发器焦点；遮罩点击是否关闭必须与风险等级一致。

## 9. UI 变更准入清单

任何影响 Web UI 的提交在合并前都应回答以下问题：

1. 是否复用了现有 CSS 令牌、圆角、间距、图标和组件模式？
2. 是否覆盖默认、hover、active、focus、selected、disabled、busy 和错误状态？
3. 是否在中文、英文、浅色、深色、跟随系统和 `prefers-reduced-motion` 下检查过文本与布局？
4. 是否在 `1440/820/560/390/320px` 检查过溢出、遮挡、重复入口和尺寸跳动？
5. 是否保持了键盘 Enter/Space/Escape、焦点恢复和屏幕阅读器标签？
6. 是否把应进入通知中心的生命周期消息错误地放进了聊天？
7. 是否更新了本规范或在提交说明中解释了有意的设计例外？

涉及交互或布局的改动至少需要 `npm run typecheck`、`npm run lint`、相关 Vitest，以及一次浏览器检查；进入发布前执行 `make ci`。截图或测试发现的视觉问题应优先修复根级令牌或共享组件，不要只给单个页面加临时覆盖。

## 10. 例外与演进

本规范不是禁止改进的冻结皮肤。以下情况可以提出设计变更：新的产品能力需要新的信息层级、现有断点无法承载目标设备、无障碍要求与现有实现冲突，或多个模块已经稳定地需要同一新模式。

设计变更必须同时更新：

- 本文对应章节和 source-of-truth 列表；
- 深色和浅色主题令牌；
- 受影响的共享组件和响应式规则；
- 中英文文案、键盘交互和浏览器验收；
- 变更提交说明中的原因和兼容影响。

局部页面的审美偏好、单次截图微调或第三方组件默认样式，不足以构成例外理由。
